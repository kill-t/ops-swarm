### 1.2 固定技术选择与参考边界

| 层次 | 选择与职责 |
| --- | --- |
| 业务系统 | 保留模块化单体、FastAPI、独立 Worker 和 PostgreSQL |
| 协作编排 | LangGraph 负责任务分派、并行、循环、checkpoint 与暂停恢复 |
| 专业 Agent | LangChain 负责模型适配、工具循环与结构化输出 |
| Harness | 项目内部轻量运行层，组织上下文、预算、工具检查、结果校验和审计 |
| 记忆与业务事实 | PostgreSQL 保存结构化记录，Git 保存版本化调查手册 |
| 工具协议 | 内部能力通过应用服务调用；日志、指标通过只读 MCP 服务访问 |
| Agent 通信 | 内部结构化任务和结果，不引入 A2A |
| 观测与界面 | 复用 OpenTelemetry、Vue 和可重放 SSE |

Harness 不重新实现框架已有调度、工具循环和 checkpoint，不增加另一套多 Agent 编排框架。框架承担基础机制，角色指令、上下文质量、工具能力和预算决定本项目允许的调查空间，不能把“框架重或轻”直接等同于 Agent 的推理质量。

A2A 留到未来对接独立部署、独立维护的外部 Agent 服务时再设计；当前保留清晰的任务与结果契约，不预建 Agent 发现、跨服务会话或 A2A 网关。

参考 DeerFlow 的模块分离、Claude Code 的任务上下文隔离与按需读取，结合本项目已有的持久业务状态落地。只采用适合当前事故场景的机制，不复制完整通用 Agent 平台；参考来源及日期见第 9 节。

执行范围继续限定本地 Docker Compose 演练环境。生产接入、复杂多租户、企业 SSO、计费、插件市场和通用代码执行沙箱不属于本版本。

## 2. 角色、自主性与协作

### 2.1 业务边界固定，调查路径动态

| 代码控制 | Agent 决定 |
| --- | --- |
| 服务范围、角色权限、参数和资源上限 | 本轮需要哪些专业任务 |
| 状态迁移、审批有效性与执行资格 | 查询顺序、窗口和补查方向 |
| 证据来源、引用完整性与结果结构 | 候选根因、竞争性解释与证据分歧 |
| 白名单动作和客观恢复判据 | 修订假设、建议方案或请求人工帮助 |

确定性校验负责结构、证据和执行条件，不把调查查询顺序全部写死。模型输出不能直接改变业务状态或扩大执行权限。

### 2.2 六个逻辑角色

| 角色 | 职责与输出 |
| --- | --- |
| 协调 Agent | 分解任务、综合专业发现，输出结构化任务与下一步安排 |
| 日志 Agent | 在日志权限内多步查询，输出异常模式、时间关联与证据 |
| 指标 Agent | 在指标权限内多步调查，输出趋势、影响范围与依赖健康证据 |
| 变更 Agent | 读取受限变更与代码来源，输出时间关联、支持证据及排除理由 |
| 审查 Agent | 独立检查反证、证据缺口和竞争性解释，提出补查或转人工建议 |
| 规划 Agent | 根据动作能力目录提出候选方案、前置条件和预期效果 |

专业 Agent 可以提出跨专业补查请求，由协调器分派，不能自行扩大权限。协调器输出经校验的结构化任务，由 LangGraph 调度；首版不开放任意递归创建 Agent 的通用工具。一个逻辑角色可以承担多个任务，不按六个角色机械拆成六个服务或队列。首版由一个调查 Worker 承载图内受限并发。

目标路径是“协调分派 → 专业调查 → 持久化结果 → 协调综合 → 独立审查 → 确定性路由”。路由可以有界补查、等待人工、终止或进入规划；图示见总路线。完成一次专业调用不等于完成整个调查。

### 2.3 未知假设与判断状态

保留既有根因分类，新增结构承载假设描述、支持证据、反证与待验证问题，兼容历史 API。未知原因可以形成调查成果；只有匹配受支持能力并通过安全校验的方案才能进入执行，不能强制映射为某个已知故障来获得执行资格。

审查通过表示当前材料满足对应审查要求，不等于根因已被客观证明。页面、专业报告与复盘保留判断状态和未解决问题；客观恢复仍由确定性验证样本判定。

## 3. 分层记忆

### 3.1 四类信息与事实来源

| 类型 | 保存内容 | 权威来源与用途 |
| --- | --- | --- |
| 任务工作记忆 | 当前目标、已查内容、发现、失败查询、未解问题及引用 | 任务记录和结构化工作摘要，供恢复及后续调用使用 |
| 事故共享事实 | 证据、报告、假设、人工补充、操作与验证结果 | 复用业务数据库，按任务范围和证据快照共享 |
| 跨事故经验 | 故障特征、调查方法、处置前置条件与失败教训 | 人工确认的版本化经验条目，辅助提出假设 |
| 调查手册 | 场景步骤、证据要求、可用工具与停止条件 | Git 管理的 Markdown 和少量元数据，按需加载 |

checkpoint 是恢复快照，不承担业务事实或长期经验的唯一存储。服务依赖、部署版本等当前信息继续由相应业务模块维护，记忆引用这些事实，不建立另一套可能过期的“当前系统状态”。

现有复盘报告是经验提取的来源，现有复盘改进行动项是工程治理记录；两者都不自动等于已启用的 Agent 经验库。

### 3.2 长期经验生命周期

1. 已关闭事故生成不可变复盘报告，复用已有报告能力。
2. 独立持久任务从报告、证据及验证结果生成经验候选。
3. 候选保存来源、适用服务、环境、故障标签、前置条件和证据引用。
4. 工程师确认、拒绝或修订；修订形成新版本并保留审核轨迹。
5. 只有有效且已确认的经验参与检索，支持停用和版本替代。

经验审核前先交付最小可信操作员身份，操作者来自服务端认证结果，不能仅依赖调用方自填的 `actor_id`。模型可以提出候选内容，启用、拒绝、停用与版本替代由应用服务和可信人工决定处理。

检索使用简单确定性规则：

- 过滤服务、环境、有效状态和适用条件。
- 按故障标签、依赖组件匹配及最近确认时间排序。
- 默认最多返回三条摘要，详情按需读取。
- 标记冻结演练与现场经验的来源，禁止无说明地跨范围混用。
- 当前证据与经验冲突时保留冲突并重新调查，经验不覆盖当前证据。
- 历史经验不能自动获得执行权限，也不能继承历史审批。

首版不引入向量数据库、知识图谱、独立记忆平台或自动学习排序。经验版本被后续停用时，新上下文不再检索它；历史上下文仍能追溯当时实际引用的不可变版本。

## 4. 上下文管理

### 4.1 ContextBuilder 与 ContextPacket

独立 `ContextBuilder` 为每次模型调用生成 `ContextPacket`，按以下顺序组织材料：

1. 当前角色指令和输出契约。
2. 任务目标、服务范围、时间窗与完成要求。
3. 必要事故状态和人工约束。
4. 分配给任务的证据摘要与引用。
5. 相关经验和调查手册片段。
6. 当前任务最近的完整模型—工具交互。

每个专业任务拥有独立上下文。协调器接收专业报告和证据目录，按需获取详情，不自动接收所有角色的完整聊天记录。所有材料先检查事故、任务、环境和证据访问范围；多个事故并发时不得串用。

### 4.2 预算与裁剪顺序

1. 范围过滤和去重。
2. 按任务相关性与时间选择材料。
3. 长结果保存为有大小上限的业务材料，向模型返回摘要和引用。
4. 用结构化工作摘要替换已完成的历史交互。
5. 保留当前任务、人工约束、反证、失败查询和未解决问题。
6. 保持工具调用与响应配对完整。
7. 必要内容仍超预算时停止本次调用，记录原因。

模型窗口必须预留输出预算和安全余量。不能静默丢掉关键约束来“塞进”窗口，也不能把被裁剪的数据描述为模型已读取。材料摘要不产生新的事实或证据引用，超过材料保存上限时显式记录截断范围。

首版复用任务输出中的结构化工作摘要，不增加独立 LLM 压缩服务。未完成的模型—工具交互不能被拆成孤立消息；工具返回的文本按不可信数据处理，不能提升为系统指令、权限或审批。

### 4.3 上下文清单与复现边界

每次调用持久化上下文清单，至少记录角色与策略版本、材料 ID、证据及经验版本、手册版本、工具集合、裁剪记录和预算估算。引用材料应能追溯到不可变内容，用于解释当时模型实际看到了什么；这不承诺重新调用模型会得到完全相同的结果。

开发协作的 `AGENTS.md` 与业务 Agent 运行时记忆分别管理，不能把整份开发约定注入所有业务 Agent。完整提示与业务材料不写入普通日志或 trace；观测只记录必要标识、用量和状态，材料访问仍经过业务权限检查。

## 5. 工具与 MCP

### 5.1 工具目录与应用服务边界

工具暴露明确、内聚的业务能力，由应用服务实现。模型不能访问整个功能模块、仓储或任意内部方法。

| 工具 | 允许角色 | 实现来源 |
| --- | --- | --- |
| `query_service_logs` | 日志 | Loki，只读 MCP |
| `query_service_metrics` | 指标 | Prometheus，只读 MCP |
| `list_recent_changes` | 变更 | 变更记录与受限 GitHub 适配器 |
| `get_service_context` | 协调及相关专业角色 | 服务、依赖和部署信息 |
| `read_evidence` | 已获证据访问范围的角色 | 持久证据及工具结果 |
| `search_incident_experience` | 协调、审查、规划 | 已确认且有效的经验 |
| `read_runbook` | 对应专业及规划角色 | 版本化调查手册 |
| `list_action_capabilities` | 规划 | 确定性动作能力目录 |

运行、任务、操作者和授权范围由系统注入；模型只在允许范围内选择查询参数。查询限制包括服务、数据源、时间窗、返回大小和超时，不接受任意 URL、SQL、Shell 或无约束查询表达式。

任务分派、报告保存、轮次推进、记忆启用、审批、执行和恢复确认由工作流或应用服务处理。模型可以输出建议，不能通过工具直接修改这些业务事实。`read_evidence` 同样检查范围，不能凭模型给出的任意 ID 读取其他事故。

### 5.2 telemetry-mcp 的本版本范围

建设独立 Compose 服务 `telemetry-mcp`，作为完整版本必须验收的只读遥测接入：

- 只提供日志和指标查询，使用固定配置的 Streamable HTTP 地址，凭据从环境变量读取。
- 复用现有遥测适配器的领域校验，按当前切片提取共享规则，避免复制两套查询规则。
- 服务端限制目标和参数，客户端检查任务与角色权限；服务不持有业务数据库写权限、环境执行权限或模型密钥。
- v2 现场调查实际通过 MCP 获取日志和指标；冻结测试继续使用假数据源。
- 断连、超时、非法响应或来源缺失显式失败，不回退到冻结证据，也不把来源失败解释为系统健康。
- 本版本不向外部 AI 客户端开放事故查询接口，不建设通用 MCP 插件平台。

MCP 负责工具与资源交互协议，记忆管理和业务授权仍属于 OpsSwarm。内部业务能力直接调用应用服务，不为统一形式强行经过网络。既有恢复验证探针和白名单执行器继续走各自确定性端口，不由调查 MCP 代理执行。

## 6. 轻量 Harness、持久化与恢复

### 6.1 按职责组织运行层

| 组件 | 单一职责 | 不承担 |
| --- | --- | --- |
| 角色定义 | 角色版本、允许工具与输出契约 | SQL、网络访问或工作流调度 |
| 任务运行器 | 组织一次任务尝试的调用与结算顺序 | 同时编写提示、授权规则和 HTTP 客户端 |
| 上下文组装 | 选择、裁剪并记录模型输入材料 | 修改业务事实、启用经验或扩大权限 |
| 工具入口 | 验证调用范围，委托应用服务或 MCP 适配器 | 任意方法反射或通用代码执行 |
| 预算策略 | 外部调用前预留共享额度，结算及检查上限 | 自建 Agent 调度框架 |
| 结果校验 | 校验结构、引用、来源和大小 | 主观替代客观恢复验证 |

以上是逻辑边界，不是本切片要创建的空目录。API、领域策略、应用用例、仓储、提示、模型与工具适配、图装配分别保持内聚职责；只在当前切片需要时提取文件，不做全仓重构，不按机械行数或一文件一函数拆分。

### 6.2 调用顺序

1. 检查任务状态、运行版本和有效租约。
2. 组装上下文并检查模型输入预算。
3. 为模型调用或工具调用预留预算并记录尝试。
4. 调用模型或受限工具。
5. 校验结构、证据引用、来源和结果大小。
6. 在有效状态与租约下持久化结果、用量及事件，再推进流程。

预算检查发生在外部请求前，所有角色、补查和重试共享所属运行预算，不能通过重试清零计数。已有用量回调与调用计数不能直接当成新的并发预算预留机制；对应切片需实现并发预留与失败结算。

复用 LangChain 工具循环、LangGraph checkpoint、OpenTelemetry 与现有用量记录。运行器组织这些机制，不能再实现一套工具循环、调度器或 checkpoint 系统。对接异步图时，阻塞适配器改用异步端口或受限线程；取消等待不等于底层请求已停止，仍需客户端超时与迟到结果防护。

### 6.3 身份、事务与恢复

明确区分事故、调查运行、轮次、专业任务、任务尝试和工具调用：

- 技术重试保留任务身份并生成新尝试；补查生成新任务，关联提出补查的报告或审查意见。
- 任务结果、证据和进度事件通过业务事务提交；checkpoint 与业务库不假设跨库原子提交，恢复时核对已提交结果并幂等结算。
- 租约失效、暂停或取消后的迟到结果不得推进流程；只记录所需的尝试、用量与审计事实。
- 外部调用前后崩溃可能造成结果不确定或重复调用，不能宣称模型恰好调用一次。未知用量保持未知，不记为零；不把估算费用护栏宣传为供应商硬性扣费上限。
- 相同查询只在同任务、同证据快照内复用；处置后和新观测窗口重新取证，旧证据保留来源、时间和适用范围。
- 等待人工时提交状态并释放 Worker，恢复命令与后续持久任务原子提交；重复命令沿用现有幂等与版本检查。
- 暂停和取消在安全边界生效，不再派发新工作；已发生费用与外部动作仍需如实结算。
- 新方案或改变执行依据的信息使相关旧审批失效，审批仍绑定精确方案版本与内容。
- 验证失败使用新样本和已执行动作创建有界重新调查，记录前序关系与回流次数，不能无限重复无效处置。

多步骤处置必须明确步骤依赖、部分失败停止和重新审批；补偿或恢复动作也受能力白名单与授权约束，不能默认所有操作可回滚。

### 6.4 版本兼容

新运行固定工作流、角色、工具、提示、输出契约、上下文与预算策略版本，并保留数据源模式和必要价格快照。保留当前工作流 v1；新协作图使用独立 v2，不静默用新图恢复不兼容 checkpoint。工作流 v2 不等于已经发布第二个产品版本。

人工恢复和验证失败回流不能绕过原有预算与动作授权。若增加预算，必须形成新的可审计控制决定，保留原始配置及增量，模型不能修改额度。具体状态、事务边界与兼容迁移在相应切片先写入数据库/API 设计，再实现。

### 6.5 类型与接口演进

| 核心内部契约 | 承载内容 |
| --- | --- |
| `AgentDefinition` | 角色、版本、工具集合与输出类型 |
| `TaskAssignment` | 目标、角色、范围、输入引用与完成要求 |
| `ContextPacket` | 模型输入、材料清单与预算信息 |
| `ToolInvocation` / `ToolResult` | 调用身份、状态、来源、结果引用与错误 |
| `AgentTaskResult` | 发现、假设、证据、跨专业补查请求与未解问题 |
| `ExperienceEntry` | 经验内容、来源、适用条件、状态与版本 |

API 按切片增加轮次/任务查询、上下文清单、人工暂停/取消/补充/恢复，以及经验候选、确认、拒绝、停用与版本查询。复用现有幂等键、乐观锁和错误格式，身份与授权范围由服务端确定。

本次只确定概念契约，不预建物理表、字段、路由或目录。每个实现切片先更新 [数据库设计](04-database-design.md) 和 [API 设计](05-api-design.md)，明确状态、持久化、接口和失败路径；未知假设以新增结构承载，既有根因枚举和历史 API 保持兼容。

## 7. 开发顺序与完整版本验收

### 7.1 按依赖交付

以下为顺序与依赖，序号不是提交编号；每行可以拆成多个独立、可验收切片。总路线同步相同顺序，变更时同时核对两个入口。

| 顺序 | 交付内容 | 主要完成标志 |
| --- | --- | --- |
| 1 | 最终架构决策落盘（第 65 步文档切片） | 长期规则、专项设计和总路线一致，明确已实现与待开发 |
| 2 | 轮次、专业任务及尝试持久化 | 并发、幂等、状态和失败路径可测试 |
| 3 | 固定图接入任务事实与最小 Harness | 中间过程可查询，预算前置，异步取证与恢复正确 |
| 4 | 上下文管理与证据按需读取 | 任务隔离、摘要、上下文清单和输入预算生效 |
| 5 | 动态专业调查与开放假设 | 专业工具循环、协调综合、跨专业补查、独立审查与有界循环 |
| 6 | 只读遥测 MCP | v2 现场调查实际通过 MCP 获取日志和指标 |
| 7 | 调查手册、可信身份与经验记忆 | 候选提取、人工审核、检索、停用与版本追踪闭环 |
| 8 | 人工介入与规划 Agent | 暂停恢复、补充信息、候选方案与审批绑定 |
| 9 | 多步骤处置与验证失败回流 | 部分失败停止、真实验证、重新调查与重复处置限制 |
| 10 | 复杂现场场景与协作工作台 | 跨服务和复合事故可演示，页面能解释并干预全过程 |
| 11 | CI、端到端验收与发布 | 新环境可部署，离线回归与真实现场演示可复现 |

必要查询接口随功能交付，完整交互页面在对应后续阶段补齐。CI 汇总在发布阶段完成，各切片测试、静态检查和进度记录从第一步持续执行。可信身份必须早于经验确认接口开放，不等到工作台阶段才补身份。

复杂现场首个场景采用“网关超时，订单服务近期存在无关发布，真实原因是 Redis 连接异常”，要求系统综合跨服务证据，排除误导性发布线索。随后增加故障先后发生、一次处置仅部分恢复、数据源不可用和旧证据冲突。

### 7.2 默认边界

- 最多三轮自动调查、三个专业任务并发、每个专业任务最多六次工具调用；任务重试不重置额度。
- 任务总数、模型调用、总时长、输入输出和费用均有显式运行配置，具体数值在对应切片验证后固定，运行开始后不能由模型修改。
- 模型窗口预留输出与安全余量，超限前停止调用。
- 经验默认最多返回三条，使用字段过滤和确定性排序。
- 首版不增加独立 LLM 压缩、向量检索或递归子 Agent。
- 人工恢复和验证失败回流遵守原预算与授权，追加预算需要可审计控制决定。
- 所有真实环境操作限制本地演练系统；“现场”表示真实采集演练遥测，不表示生产接入。

### 7.3 必须通过的测试

- 动态任务分派、跨专业补查、反证处理和未知根因表达。
- 两个事故并发时上下文、证据和经验范围不串用。
- 长日志与摘要裁剪保留关键约束、反证、失败查询及工具消息配对。
- 未确认、已停用和范围不匹配的经验不进入新上下文，历史材料仍可按版本追溯。
- 恶意工具文本不能改变系统指令、权限或审批。
- 并发预算预留正确，调用前拒绝超额，重试不能重置额度。
- MCP 超时、非法响应和来源缺失具有明确失败语义，不能回退到冻结证据。
- Worker 在调用前后和业务提交边界崩溃时正确恢复，未知用量不记为零。
- 人工重复恢复、取消后迟到结果和旧 checkpoint 兼容检查。
- 计划变更使旧审批失效，多步骤部分失败安全停止。
- 验证失败回流、重复无效处置限制和终止上限生效。
- 完整现场演示串起多 Agent、上下文、记忆、MCP、人工审批和恢复验证，界面刷新与 SSE 重连可恢复显示。

Agent 自动化测试默认使用假模型和固定工具结果；数据库使用真实 PostgreSQL。真实模型调用仅用于显式授权的场景验收，不能成为 CI 前提。发布记录分别保存冻结回归与现场结果，包括协作发现、补查、恢复、耗时、工具调用、Token 和估算费用，不提前编造改进百分比。

### 8.2 状态和继续开发流程

- **已决定**：方向确定，能力尚未实现。
- **开发中**：代码或接口正在建设，尚未完成验收。
- **已验收**：有对应实现、提交和可复现验证记录；文档切片须明确验收对象只是文档。

每次继续开发时：

1. 阅读 `AGENTS.md`、当前架构入口与最新进度记录。
2. 检查 Git 状态及当前相关代码，确认未提交变化。
3. 明确当前切片、已完成前置条件与本轮验收目标。
4. 根据实际测试结果更新进度和能力状态，不沿用历史测试数量当作本轮结果。
5. 架构调整先更新事实来源，再修改代码和进度记录。

不能根据聊天中的完成表述、计划图或文件名判断能力已实现；不能把模拟数据写成现场证据，把人工业务审批写成已实现的图内暂停恢复，或把参考项目能力写成 OpsSwarm 的现有成果。
