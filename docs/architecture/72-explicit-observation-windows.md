# 现场来源的显式观测窗口

## 1. 交付边界

第 72 步为 Loki、Prometheus 和本地变更服务增加显式窗口查询能力，供后续现场 v2 任务使用。现有相对时间查询、v1 Worker 和冻结 v2 保持原行为；本片不开放现场 v2，不新增任务策略或迁移，不接入 MCP、GitHub 历史查询或当前运行清单的任务化采集。

## 2. 时间契约

`ObservationWindow` 是只负责 UTC 时间范围的不可变契约，要求带时区、Unix 起点之后的整秒时间、正区间、最长 24 小时。使用闭区间，不静默舍入调用方时间。日志与指标进一步限制为 1～60 个完整分钟；变更支持最长 24 小时。请求前拒绝未来截止时间。查询期间和重试时使用传入窗口，不重新以当前时钟移动起止点；当前时钟仅用于检查未来窗口和响应新鲜度。

Prometheus 使用原有秒级参数；Loki 使用纳秒参数，其远端截止点不包含自身，因此将传输截止点加一纳秒，再按原业务截止点严格校验响应。日志内部时间和流时间都必须落在原窗口内，不能借旧路径的时钟容差扩大显式范围。

日志和指标保留固定查询、服务白名单与既有响应校验。显式查询严格拒绝窗口外的响应；Loki 同时检查流时间与日志内事件时间，Prometheus 的健康查询固定在截止时间。指标证据代表区间聚合，附带查询起止时间；不能把查询截止时间当作最新原始抓取时间。日志空结果允许返回空集合，指标缺失依旧明确失败，不当作健康状态。

固定查询窗口不等于上游不可变快照。Loki、Prometheus 可能迟到写入或删除数据；只有第 71 步已提交的业务快照可用于稳定恢复。未提交前重新查询可能获得不同材料，不能声称请求或内容恰好一次。

## 3. 变更历史与当前运行状态

新增只读 `GET /api/v1/changes/window`，要求 `service_name`、`window_start`、`window_end`，返回明确回显的窗口和 `generated_at`。过滤发生时间在窗口内、且 `recorded_at <= window_end` 的记录，截断状态仍显式返回。窗口截止后才入库的旧事件不属于“截止当时已知事实”，后续新窗口或补查再读取；`generated_at` 是本次响应生成时间，不能冒充历史截止时间。

这里的 `recorded_at` 是摄取服务记录的时间，并非 PostgreSQL 事务提交时间；该过滤不等于数据库历史时点快照。查询时尚未提交的事务随后可能可见，材料仍需通过第 71 步的独立业务快照固定。响应中的 `window` 回显原始查询范围，空结果同样回显，不能从本次生成时间重新推算。

新增变更适配器窗口入口，复用 HTTP 限制和记录校验，核对回显窗口、发生及入库时间、重复记录、截断和响应新鲜度。这里只生成历史变更证据，不请求当前运行清单，也不推断哪个历史发布仍在运行。当前部署实例、签名有效性和滚动发布状态仍由原有实时核对路径负责；后续需独立采集时间、材料契约和权限，不能与历史事件共用一个时间戳。

变更仓储在已有过滤上增加可选入库截止条件；原端点和默认仓储调用保持兼容。没有数据库结构变化。非法窗口或服务在外部访问前失败；来源断连、异常响应与截断不回退到相对查询或冻结材料。

## 4. 验收与下一步

假 HTTP 验证调用中时钟推进仍保留原窗口、查询参数准确、严格时间边界、空结果、来源失败和历史变更不访问运行清单。真实 PostgreSQL 验证发生时间与入库时间双重过滤、未来/非法窗口拒绝、截断和原端点兼容。

后续将运行级截止时间、现场材料契约、异步端口与第 71 步快照接入 v2，并明确 GitHub 组合模式和当前运行清单的任务契约；不静默丢弃已配置来源。
