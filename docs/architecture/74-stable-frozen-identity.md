# 74 - 冻结场景身份的确定性与历史兼容

## 目标与状态

本片已实现并通过自动化验收，结果见 [进度记录](../progress/74-stable-frozen-identity.md)。第 73 步发现旧 `FrozenScenarioDataSource.snapshot_id` 直接散列 Pydantic JSON，其中 `required_evidence_ids` 是集合，序列化顺序随进程哈希种子变化。本片修复身份生成与旧任务恢复，不增加上下文或动态协作能力。

## 新身份

- 新身份使用 `frozen-v2:<sha256>`，身份版本与工作流 v2、取证策略版本分别管理。
- 先把场景转换成 JSON 值，将 `required_evidence_ids` 排序，再按对象键排序、固定紧凑分隔符和 UTF-8 编码计算散列。证据数组仍保留原顺序，场景内容、来源、时间、预期答案变化会改变身份。
- 不改变场景文件、评测真值、专业取证快照格式或其内容散列算法。现场运行继续使用第 73 步固定身份。

## 历史身份的有限兼容

- 发布过的三个内置场景及对应 v2 版本共六份内容，分别有两到三个必需证据 ID；离线枚举旧集合的两种或六种排列，按原 Pydantic JSON 字节规则生成旧身份表。运行时只查表，不枚举排列、不猜测哈希种子。
- 表以完整的新内容身份为键，列出对应内容的旧身份（共 20 个）；场景任何实质变化都会失去旧身份授权。仅兼容这六份已发布内容，不假装能够恢复无法证明内容的任意自定义旧场景。
- 准备冻结 v2 任务时，先校验有效租约，再读取业务任务范围。只有所有任务使用同一个、且属于当前场景兼容表的旧身份时，运行器才沿用该身份重建原分派。
- 继续调用 `create_round` 的事务性幂等核对，完整核对目标、角色、窗口、任务范围和分派散列，并补充任务表与分派内容的一致性核对；不能只凭旧身份绕过其他约束。混用、未知身份、内容改变或范围改变均拒绝推进，不调用模型或外部工具。
- 新任务使用新身份；已有旧任务、取证快照、报告、事件和 checkpoint 不重写、不回填。无取证策略的历史 v2 仍按原方式取证，有策略的历史 v2 仍复用已提交快照，预算不清零。
- v1 没有持久专业任务身份，保留原图路由；新旧图版本检查仍生效。

## 数据库与 API

不新增表、字段、接口或迁移。身份长度继续符合现有 100 字符约束；API 返回任务实际持久化的身份，旧任务仍返回旧值。兼容采用内容身份授权，不改写现有业务事实或伪造迁移审计。

## 验收要求

- 不同 `PYTHONHASHSEED` 的独立解释器产生相同新身份，字典插入顺序不影响身份；内容改变必须改变身份。
- 六份发布内容的全部旧排列均被准确识别；未知、自定义及改变内容的旧身份不被接受。
- 在真实 PostgreSQL 与独立 checkpoint 数据库中，由不同哈希种子的独立 Worker 进程执行失败及恢复，覆盖新任务与旧任务、有无取证快照、预算计数及原材料散列保留。
- 拒绝混合任务身份与修改后的场景；回归现场 v2、固定图、预算、取证快照和版本检查。默认假模型，不使用真实模型或外部遥测。
