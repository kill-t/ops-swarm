# 协调模型结构化调用与共享预算账本

## 目标与边界

本片把第 82 步的有限协调提案和第 83 步的计划事实接到一次真实的 LangChain 结构化模型调用。协调调用使用运行级共享次数、时限、Token 与估算费用预算；成功返回保存到业务调用账本，并成为轮次计划可复核的来源。

这是接入动态图前的内部应用服务切片。当前仅支持具有 `function_calling` 模型预算、固定证据策略和冻结数据源的 v2 运行，并且只创建第一轮；没有新增 HTTP 参数、Worker 路由、v3 图或第二轮上下文。旧 v1/v2 图不会调用该服务。

## 输入、权限与预算

新增根级 `coordinate` 操作。它必须使用调用序号 0，不绑定专业任务或专业尝试，并与所有专业和综合调用共享原有运行预算。数据库同时约束操作种类、根级范围、调用序号和输入/返回版本。

`coordination-model-input-v1` 保存轮次、已有任务数、系统确定的 UTC 截止时间和快照身份、两条文本消息、输出 Schema 及工具 Schema。上下文清单使用独立的 `coordination-context-v1` 和 `dynamic-coordinator-v1`，只引用事故输入与已固定协调策略；工具集合为空，因此协调 Agent 不能读取任意证据、创建 Agent 或获得执行权限。该内部上下文版本不属于运行创建 API 可选的任务上下文策略。

协调策略在任何外部请求前通过有效父租约固定。模型返回先经过 Pydantic 校验，再由确定性编译器验证任务键、角色窗口、轮次和运行任务额度；只有业务规则也通过时，调用才以 `succeeded` 保存 `coordination-model-result-v1`。Schema 合法但越权的提案以失败调用结算，不会成为后续恢复反复复用的成功来源。

## 来源绑定与恢复

迁移 `0042_coordination_model_call` 为协调计划增加可空 `source_call_id`，并以运行 ID 组成复合外键指向调用账本。可空字段保留第 83 步无模型来源的既有计划；通过模型创建的新计划必须由应用服务提供成功来源。

读取计划时继续从事故、策略、轮次和任务重建，并额外验证来源调用属于同一运行、为根级成功 `coordinate`、上下文及模型分配可重建、原始 JSON 是规范形式、提案与计划相同、截止时间和快照一致，且调用先于计划完成。数据库复合外键阻止跨运行引用，应用层负责验证调用操作、状态和内容语义。

恢复分为三种情况：

- 模型请求尚未得到可确认结果时，原预留保持失败或未知；新父尝试使用新的稳定预留身份，预算不会清零。
- 模型成功、计划尚未提交时，新父尝试从账本复核并复用成功提案，不再发第二次外部请求。
- 计划已经提交时，新父尝试先复核并返回原计划，不再准备上下文或调用模型。

同一运行存在多个成功首轮协调调用、成功来源上下文不同或恢复参数变化时明确拒绝。该设计提供可恢复业务幂等，不宣称供应商请求物理上恰好一次。

## 失败路径与后续

不支持的工作流、数据源、证据策略、模型输出方式或预算配置在固定协调策略前拒绝，不留下混合历史。非法时间、快照、上下文、调用序号、来源、租约及内容篡改均返回稳定冲突；计划、轮次、任务和事件仍在一个父租约事务内提交。

下一片为新动态工作流定义独立版本，在运行创建时冻结协调、上下文、预算和图版本，再把首轮规划服务接入新的 LangGraph 图。后续切片再引入任务结果摘要、第二轮定向补查与确定性停止条件。
