# 23 - 只读评测面板

## 目标

为已经持久化的评测运行提供第一个只读页面，使学习者和值班工程师能够浏览历史运行、比较单 Agent 与多 Agent 的核心指标，并检查每个冻结场景的根因、建议和证据引用。

## 设计与边界

- 新增 `/evaluations/:runId?` 路由，选中运行保存在 URL 中，详情页刷新后可恢复。
- 历史列表复用后端 `before_sequence` 游标，支持“加载更早运行”，不使用不稳定的 offset 分页。
- Pinia store 使用列表与详情两套 generation，防止较早请求晚返回时覆盖最新状态。
- 页面只调用两个评测 `GET` 接口，不提供启动、修改或删除评测的能力。
- 聚合表固定显示六项指标，差值统一为“多 Agent − 单 Agent”；逐场景展示冻结真值、执行顺序和证据 ID。
- 页面显式说明当前是假模型契约评测，避免把 100% 分数解释为真实模型或多 Agent 优势。
- 未引入图表库；当前一个历史样本用精确数值表比趋势图更有信息量。

## 实际改动

- 新增评测 API 类型、只读客户端和 Pinia store。
- 新增评测运行列表、指标与逐场景详情组件。
- 新增评测面板视图和可刷新详情路由。
- 把原作战室头部提升为全局应用头部，增加“事故作战室 / 评测面板”导航。
- 增加桌面、平板和 390px 窄屏布局，保留本地演练环境标识和可访问性语义。
- 增加 API、store 和详情组件测试夹具与测试用例。

## 限制与下一步

- 本地库当前只有一轮运行，真实多页翻页仍需在积累更多运行后做浏览器验证。
- 当前数据来自冻结假模型，满分不能证明多 Agent 优于单 Agent。
- 数据模型还没有真实模型名、提示版本、Token、成本、失败分类和重复试验分布，页面不会提前伪造这些字段。
- 下一切片先设计真实模型评测记录边界，再决定是否增加趋势、成本和失败分析页面。

## 面试表达

我没有直接画一张漂亮但不可追溯的 Agent 分数图，而是先把评测面板建立在 PostgreSQL 审计事实和稳定只读 API 上。URL 保存运行选择，服务端游标保证历史分页稳定，Pinia generation 解决异步竞态。页面同时展示报告哈希、聚合指标和逐场景证据，并主动提示假模型满分的解释边界，因此既可演示多 Agent 对照，也不会夸大实验结论。
