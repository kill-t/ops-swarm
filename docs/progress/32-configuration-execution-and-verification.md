# 32 - 配置回滚受控执行与恢复验证

日期：2026-08-29

## 目标

把数据库连接池配置回滚从不可执行草案推进为经过人工审批、当前值复核、幂等执行和持久恢复验证的完整本地链路。

## 设计与边界

- 客户端不能提交配置键、配置值、URL 或 HTTP 方法。
- 配置动作必须经过当前计划的精确人工批准。
- 执行前读取当前值；已是目标值按安全重放处理，值已漂移则拒绝覆盖。
- 真正写入使用 `expected_value` 原子比较并设置，防止读写竞态。
- 配置失败与 Incident 回流原子落库。
- 验证只读取固定连接池状态路径，客户端不能伪造饱和度。
- 本切片仍只操作本地 Docker Compose 故障实验室。

## 实际改动

1. 为连接池更新请求增加可选严格 `expected_value`，控制器在同一锁内比较并设置。
2. 为配置漂移增加结构化 `409 database_pool_value_conflict`。
3. 扩展审批动作白名单，允许配置草案进入人工审批。
4. 扩展 `FaultLabOperationAdapter`，支持固定配置回滚、当前值复核、CAS 和安全重放。
5. 为版本与配置动作分别保存稳定执行器名称，完成事件使用实际执行记录名称。
6. 扩展 `FaultLabVerificationAdapter`，读取 `database_pool_saturation`。
7. 扩展验证领域判定与仓储白名单，支持两个动作对应的精确信号。
8. 新增 `0015_configuration_execution`，扩展执行器、验证器和信号数据库约束。
9. 把数据库连接池控制面测试从“审批阻断”升级为计划到恢复样本的完整链路。
10. 更新 README、数据库、审批、执行、验证和配置计划架构文档。

## 测试方法与结果

已完成的定向验证：

- 48 项故障控制、CAS、执行与探针测试通过。
- 45 项审批、执行、验证、控制面和迁移真实 PostgreSQL 测试通过。
- 配置控制面链路完成 `draft → awaiting_approval → mitigating → verifying`，并保存饱和度成功样本。
- 真实 Compose 容器完成 `5 → 50` CAS，饱和度为 `0.2`；漂移到 `7` 后旧预期值返回 `409` 且保持 `7`，最后恢复为 `50`。
- 本地业务库升级到 `0015_configuration_execution (head)`，`alembic check` 无漂移。

最终验收结果：

- 全量 `303` 项测试通过。
- Ruff 规则检查通过，`245` 个 Python 文件符合格式规范。
- mypy 检查 `109` 个源码文件无类型错误。
- `alembic check`、`docker compose config --quiet` 和 `git diff --check` 通过。
- `control-db` 与 `order-service` 容器均为 `healthy`；最终连接池值为 `50`、饱和度为 `0.2`、等待请求为 `0`。
- 测试未调用真实模型，不消耗模型 API token 或费用。

## 限制与下一步

- 当前连接池状态仍是单进程确定性模拟，不是真实数据库连接池。
- 恢复采样仍需调用方手动触发，没有持久定时调度。
- 配置漂移后会可靠回到调查，但不会自动启动新的调查任务。
- 下一步优先实现持久验证调度器，自动按冻结观察窗口触发样本并支持重启恢复。

## 面试表达

配置回滚最大的风险不是“接口能不能 PUT”，而是审批后环境可能已经变化。我把计划当前值纳入 CAS：环境等于计划当前值才修改，已经是目标值允许崩溃重放，其他值一律拒绝并回到调查。执行成功后还要用固定饱和度探针经过三次样本和 60 秒窗口才能解决 Incident。这样既保留至少一次执行的可恢复性，又不会让重试覆盖新的人工配置。
