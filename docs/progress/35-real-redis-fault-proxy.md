# 35 - 真实 Redis 与受控故障代理

日期：2026-08-30

## 目标

把 Redis 不可用场景从进程内布尔模拟升级为 Docker Compose 中可见、可真实访问、可确定性断开的 Redis 依赖，同时保持 LLM、执行器和订单服务都没有 Docker Socket 或任意基础设施权限。

## 设计与边界

- `lab-redis` 是独立真实 Redis 容器，仅加入故障实验室私有网络。
- `redis-proxy` 的后端固定为 `lab-redis:6379`，不能代理任意目标。
- 订单服务使用 redis-py 经代理执行真实 `PING`，不再用本进程布尔值冒充 Redis 健康。
- 代理禁用时会关闭已有连接，防止连接池绕过故障。
- 外部执行器继续调用原有订单管理接口；订单服务才访问代理固定管理端点。
- 故障开关可丢失并在重启后恢复安全默认值；业务操作和验证审计继续持久化到 PostgreSQL。
- 本切片不修改业务数据库，不新增迁移，也不调用模型。

## 实际改动

1. 增加 redis-py 依赖和受限 Redis、代理管理地址配置。
2. 为订单服务拆分本地测试后端与真实网络后端，Compose 入口默认访问真实 Redis。
3. 新增异步 TCP 双向代理、已有连接清理、CAS 状态控制和固定管理 API。
4. Compose 新增 `lab-redis`、`redis-proxy`，配置健康检查、私有网络、只读文件系统和最小容器权限。
5. 订单服务依赖真实代理健康后启动，并继续向执行器暴露稳定的 Redis 管理契约。
6. 新增代理字节转发、连接中断、恢复、CAS、严格布尔、配置限制和真实后端错误映射测试。
7. 更新 README、系统架构、技术栈和上一切片的后续状态。

## 测试方法与结果

- `docker compose config --quiet` 通过。
- 全量 344 项测试通过，包含新增代理测试、真实 PostgreSQL 集成测试和既有 Agent、审批、执行、验证回归。
- Ruff 规则检查通过，262 个文件格式正确。
- mypy 检查通过，113 个源码文件没有类型错误。
- Alembic 数据库与 ORM 元数据一致，没有遗漏迁移。
- Compose 构建并启动后，`lab-redis`、`redis-proxy`、`order-service` 与控制面数据库均健康。
- 真实 Redis `PING` 返回 `PONG`。
- 代理可用时订单返回 `200`；CAS 切断后订单稳定返回 `redis_connection_unavailable` 和 `500`；恢复后订单重新返回 `200`。
- 演练结束后代理已恢复为 `available=true`。
- `git diff --check` 与 Compose 配置检查通过。

首次拉取 Redis 后，Docker Hub 曾在读取 Python 基础镜像元数据时临时返回 EOF；重试后镜像成功构建。这属于外部镜像仓库瞬时失败，不是代码或 Compose 配置错误。

## 限制与下一步

- 只支持确定性完全断连，不模拟延迟、丢包和 Redis 主从故障。
- Redis 仅用于本地无鉴权演练，不可部署到生产。
- 调查数据仍是冻结证据，真实 Prometheus 和 Loki 尚未接入。
- 下一步接入真实 Prometheus 指标，使调查与验证逐步读取真实遥测。

## 面试表达

我用固定 TCP 故障代理把“真实依赖访问”和“最小恢复权限”同时保留下来。订单服务真的执行 Redis PING，但 Agent 与执行器都不能操作容器；代理只能对固定 Redis 做 CAS 连通切换，并在断开时清理已有连接。这样既能稳定复现故障，又不会为了自动化牺牲安全边界。
