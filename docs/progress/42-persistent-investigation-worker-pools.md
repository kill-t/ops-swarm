# 第 42 步：冻结与现场常驻调查工作池

## 本步目标

消除 API 投递调查后需要人工反复执行单次 Worker 命令的运维空档，同时保留持久租约、失败重试、数据源隔离和本地安全边界。

## 设计决策

- 默认 CLI 改为常驻轮询，保留 `--once` 作为显式诊断入口。
- Compose 中固定部署 `investigation-worker-frozen` 和 `investigation-worker-live`，不让运行时任务切换数据来源。
- 空闲轮询由停止事件中断；停机后停止领取新任务，但让已领任务在有界超时内完成结算。
- 处理超时必须小于租约，容器停机宽限覆盖处理超时，避免无界等待。
- 处理超时复用已有安全错误摘要、指数退避和任务状态结算，不建第二套失败机制。
- 工作池容器保持只读根文件系统、最小 Linux 权限和网络分池；Jaeger 不作为业务启动前置。

## 实现内容

1. 调查 Worker 新增常驻循环、可中断空闲等待、处理硬超时和有限字段日志。
2. Worker 配置新增轮询、租约、处理超时、基础与最大退避，并校验它们的交叉关系。
3. CLI 在 Linux 容器注册 `SIGTERM/SIGINT`，Windows 仍使用 Psycopg 兼容事件循环，手工中断可正常释放资源。
4. Compose 新增冻结与现场工作池，共用运行镜像与配置护栏，但保持不同网络权限和数据源模式。
5. 对空白 `LLM_BASE_URL` 做未设置归一化，兼容 Compose 环境变量缺省值。
6. 更新 README、环境变量模板、系统架构、技术栈和 Worker 事实文档。

## 测试与验收

完整验收命令：

```powershell
uv run ruff format --check .
uv run ruff check .
uv run mypy
uv run pytest
docker compose config --quiet
cd web
npm run typecheck
npm test
npm run build
```

自动化测试覆盖常驻/`--once` 入口、无效时间窗口、空闲停机、在途任务结算、硬超时重试和空白兼容地址。Compose 验收要求两个 Worker 容器都保持运行，无待处理任务时不产生模型调用。

实际结果：320 个文件通过格式检查，Ruff 通过，mypy 严格检查 137 个源码文件通过，467 个后端测试全部通过。前端类型检查通过，7 个测试文件中的 14 个测试通过，生产构建成功。Markdown 相对链接、Compose 解析和 `git diff --check` 通过。

本地容器验收中，`investigation-worker-frozen` 与 `investigation-worker-live` 均保持运行并显示正确的数据源模式。业务库中无 `pending/running` 调查任务，因此未触发模型调用。冻结工作池完成一次空闲优雅重启后再次进入常驻轮询，容器自动重启计数仍为 0；临时 `--once` 容器也能识别无可用任务并正常退出。

## 为什么这样设计

数据库持久队列已经解决了任务不丢失和并发领取，因此常驻化只需解决轮询与生命周期，没有必要引入第二个队列系统。将处理超时、租约和容器宽限建立明确大小关系，可以在优雅停机、任务接管和不无限等待之间得到可验证边界。

## 限制与下一步

- 后续切片已经建立逐次 Worker 尝试业务记录，并在作战室展示状态、Token 与费用完整性。
- 未来如果数据证明单次调查应超过当前有界时间，需要增加安全租约续期，而不是直接设置过大固定租约。
- 下一步根据积累的尝试历史评估租约续期与并发容量，不用日志或 trace 反推成本。

## 面试表达

我没有为常驻化再引入 Celery 或 Redis，因为 PostgreSQL 租约队列已经承担可恢复业务语义。我把冻结和现场调查拆为两个独立工作池，并使处理超时小于租约、容器宽限覆盖处理时间。停机信号只阻止新领取，已领任务仍会通过原有成功或重试事务结算，所以重启行为可解释、可测试。
