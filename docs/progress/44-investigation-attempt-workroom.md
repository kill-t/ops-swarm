# 第 44 步：作战室调查尝试与成本展示

## 本步目标

在 Incident 作战室只读展示当前调查的逐次 Worker 历史，让失败、重试、租约过期、耗时、Token 和费用完整性成为值班工程师可以直接核对的信息。

## 设计决策

- 保留六阶段聚合投影的单语句快照职责，尝试明细继续读取独立只读接口。
- 只能使用当前作战室快照中的调查运行 ID，不允许页面拼接任意调查。
- Incident 选择代次、作战室请求代次、Incident ID 和 run ID 共同保护异步响应。
- 尝试加载失败不破坏已经成功读取的处置链路摘要。
- 用量不完整、价格缺失和运行中分别解释，未知费用不显示为 `$0`。
- 页面继续保持只读，不新增模型调用和外部写操作。

## 实现内容

1. 新增调查尝试 TypeScript 契约和 API 客户端方法。
2. Pinia 在作战室同步后读取当前运行的尝试历史，并维护独立加载与错误状态。
3. 新增 `InvestigationAttemptHistory` 组件，展示状态、耗时、请求、Token、费用、错误和重试结果。
4. 补充宽屏与手机布局、状态颜色、费用未知提示和可访问性属性。
5. 增加 API、状态竞态、组件语义和空状态测试。
6. 更新 README、前端架构、尝试审计和进度事实文档。

运行态复查确认冻结与现场调查 Worker 继续保持常驻，业务库没有待处理或运行中的调查任务，尝试表也没有因本次 UI 验收新增记录。因此本切片没有发起真实模型请求，也没有产生模型费用。

## 为什么这样设计

尝试记录是调查运行明细，不应破坏作战室六阶段投影的固定摘要和单语句一致性。前端分两步读取会产生迟到响应风险，因此不能只靠组件当前路由判断，而要同时绑定 Incident 和调查运行，并使用请求代次拒绝旧结果。

## 限制与下一步

- 尝试内部变化没有独立 SSE 事件，运行中页面通过“同步”按钮刷新。
- 当前未分页，但 MVP 的最大重试次数有界。
- 后续第 45 步已选择 GitHub 并建立固定仓库的只读变更适配，模型仍无写权限。

## 面试表达

我把增长型运行明细与核心聚合快照分开读取，并在 Pinia 中使用 Incident ID、run ID 和请求 generation 处理异步竞态。页面不会把空费用解释为零，而是根据用量完整性和价格快照展示具体未知原因，因此成本数据对值班和评测都有可解释性。
