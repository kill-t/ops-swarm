# 第 47 步：作战室展示部署代码来源

## 本步目标

把第 46 步持久化的部署版本、仓库、完整 Commit SHA 和匹配状态展示到 Incident 作战室，让值班工程师不离开事故上下文就能审查软件来源。

## 设计决策

- 复用既有 Evidence Board 明细接口，不修改数据库或核心作战室聚合响应。
- 调查尝试和 Evidence Board 按当前 run ID 并行读取。
- 使用 Incident、run ID、选择代次和请求代次共同丢弃迟到响应。
- 页面只选择确定性部署 Evidence，不把普通 GitHub Commit 当成已经上线。
- 展示匹配前再次核对关联 Evidence；外链使用严格 GitHub Commit URL 白名单。
- 历史 Evidence 同时缺少状态、仓库和 SHA 时显示 `未声明代码来源`，不误报异常。
- 页面保持只读，不增加审批、执行、GitHub 写入或模型权限。

## 实现内容

1. 增加 Evidence Board 前端最小读取契约与 API 客户端。
2. Incident Store 增加 Evidence Board 独立加载、错误状态和迟到响应保护。
3. 新增部署代码来源组件，展示版本迁移、仓库、完整 SHA、状态说明和安全外链。
4. 增加桌面与窄屏布局，长 SHA 不产生横向滚动。
5. 补充 API、Store、组件状态、历史兼容、引用不一致和非白名单链接测试。

## 测试与验收

完整验收结果：

- Ruff 格式检查确认 336 个文件无需调整，静态检查通过。
- mypy 检查 141 个 Python 源文件通过。
- 后端 500 项测试全部通过。
- 前端 9 个测试文件共 26 项测试通过，类型检查与生产构建通过。
- Docker Compose 配置检查通过。
- 真实浏览器读取旧事故时，升级前的部署 Evidence 正确显示为 `未声明代码来源`。
- 真实浏览器读取新建 `INC-000003` 时，页面显示 1 条已精确匹配部署事实、固定仓库、完整 SHA 和白名单 GitHub Commit 链接。
- 390px 视口下事实区域切换为单列，页面和组件均无横向溢出；浏览器控制台无错误。

## 真实现场冒烟

本轮在本地故障演练环境短暂启用 `release_500`，四次订单请求稳定返回 500，然后创建独立 Incident 并启动单 Agent 真实现场调查：

- 调查使用 `deepseek-v4-flash` 并成功完成；
- Evidence Board 保存 8 条证据，其中 1 条部署事实为 `matched`；
- 模型调用 2 次，总计 4,905 Token，估算费用为 0.002799 美元；
- 没有审批或执行处置，没有写入 GitHub；
- 冒烟结束后故障开关已关闭，订单接口恢复 200。

真实密钥仍只存在本机 `.env`，页面、日志、测试和 Git 差异均不包含令牌值。

## 为什么这样设计

Evidence Board 已经是调查证据的业务事实来源，另做一套“部署展示 API”会复制筛选和可信度规则。前端复用明细接口，同时保持核心作战室聚合轻量。页面对 `matched` 和外链做纵深复核，是为了让 UI 即使遇到历史数据或异常属性，也不会比后端证据宣称更高的可信度。

## 限制与下一步

- 当前展示调查时保存的快照，不会在浏览器中重新查询 GitHub。
- 部署代码引用在本步骤仍由本地管理接口显式写入；第 48 步已经补充带来源身份、幂等编号和白名单仓库校验的 CI/CD 部署事件摄取接口。

## 面试表达

我没有扩充高频核心聚合，而是按当前调查运行并行读取 Evidence Board，并用两级 generation 防止迟到响应串事故。UI 只展示确定性部署事实，复核仓库、完整 SHA、Evidence ID 和 GitHub URL 白名单；历史记录缺少新字段时保持诚实的 `not_declared`。最后用真实模型调查和真实浏览器验证了从部署事实到工程师可见证据的完整链路。
