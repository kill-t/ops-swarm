# 52 - Ed25519 签名运行清单证明

## 目标

给第 51 步的多实例运行清单增加可验证来源，同时不把签发权交给订单服务、调查 Worker 或 Agent。证明必须短时有效、可轮换、绑定当前进程，并在任何篡改或过期场景下失败关闭。

## 设计与边界

- 使用 Ed25519 非对称签名：独立控制器持有私钥，订单服务只持有公钥环。
- 签名覆盖证明 ID、固定受众、服务名、签发/过期时间、完整实例集合和发布窗口。
- 单份证明最长 5 分钟，公钥环最多 4 把，通过 `key_id` 支持先加新钥、后切签发、再删旧钥。
- 证明必须精确包含当前进程的 UUID、镜像仓库和 digest，否则订单服务拒绝启动。
- 查询时重新验签并检查时效；过期返回专用 `503`，不会降级到未签名声明。
- 未签名环境声明继续兼容，但与签名模式互斥，并在 Evidence 和页面中明确标记。
- Agent、浏览器、Compose 和白名单执行器都没有私钥、任意 Shell、Docker Socket 或 Kubernetes 凭据。

## 实际改动

- 增加 `cryptography` 依赖，使用库提供的 Ed25519 原语，不自行实现密码算法。
- 新增签名载荷、信封、公钥环、规范化 JSON、签发、验签、时效检查和进程绑定模块。
- 扩展运行清单设置和响应模型，限制证明 64 KiB、公钥配置 4 KiB，并严格约束来源与证明摘要组合。
- 订单服务启动时首次验签，每次读取清单时再次检查；未签名响应保持原字段，不新增空 `proof`。
- Compose 与 `.env.example` 增加证明和公钥环变量，但没有私钥变量。
- 调查 Evidence 保存 `verified`/`unsigned`、证明 ID、密钥编号、算法和有效期。
- 作战室复核 UUID、密钥编号、算法、时序和 5 分钟上限，显示已验签、未签名、历史未签名或异常。
- 更新 README、第 51 步文档和完整架构事实来源。

## 限制与下一步

- 证明仍通过启动环境注入，过期后不能在线刷新。
- 当前只有纯签发函数，没有独立常驻部署控制器服务或私钥存储适配器。
- Worker 信任订单服务的验签结果，不做第二次端到端密码学验证。
- 证明认证控制器声明，不代表实例存活、Ready、流量比例或镜像供应链签名。
- 下一步实现独立本地部署控制器模拟器和受限证明刷新协议，再评估 Kubernetes 固定 namespace/workload 的只读适配器。

## 面试表达

> 我没有让业务服务和 Agent 共用一个 HMAC 密钥，因为那会让验证方同时具备伪造能力。独立控制器用 Ed25519 私钥签完整运行清单，订单服务只保留最多四把轮换公钥。证明固定受众、最长五分钟，并绑定当前进程 UUID、仓库和 digest；篡改、未知 key、过期或绑定不一致都会失败关闭。Evidence 只保存验签摘要，页面明确区分已验签与未签名来源。当前证明还是启动时注入，下一步才做独立控制器和动态刷新。
