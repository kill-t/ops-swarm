# 58 - 确定性事故复盘报告快照

## 目标

为 `closed` Incident 生成一次持久、可追溯、可幂等读取的结构化复盘报告，使完整处置闭环不再只散落在多张业务表中。

## 设计与边界

- 报告只聚合已提交到 PostgreSQL 的 Incident、作战室处置链路和追加式时间线，不调用模型补写内容。
- 首次生成必须满足 `closed` 和乐观锁版本匹配；已存在报告直接幂等返回。
- 报告内容使用 `incident-report.v1` 严格结构并保存 SHA-256，读取时重新校验。
- 复盘时间线最多 500 条，超过上限明确失败，不返回不完整快照。
- 本步不做 Markdown/PDF 导出、前端报告页、身份认证或行动项管理。

## 实际改动

- 新增 `reports` 模块，包含报告模型、领域错误和 PostgreSQL 仓储。
- 新增 `incident_reports` 表及 Alembic 0027 迁移，每个 Incident 最多一份报告。
- 把作战室聚合查询开放为同会话函数，让页面读取和报告冻结共享选择规则。
- 新增报告生成和当前报告读取接口，并映射未就绪、不存在、超限和完整性错误。
- 增加报告关闭前拒绝、首次生成、幂等重试、持久读取和 OpenAPI/迁移契约测试。

## 测试方法与结果

执行报告 API 定向测试：

```powershell
uv run pytest tests/api/test_control_plane_api.py -k "incident_report"
```

结果为 `3 passed`。覆盖未关闭拒绝、未生成读取、关闭后快照、最终时间线、内容摘要、旧版本幂等重试、并发请求共享唯一快照和 GET 持久读取。

执行 OpenAPI 与迁移元数据检查：

```powershell
uv run pytest tests/api/test_control_plane_openapi.py tests/integration/test_migrations.py
```

结果为 `4 passed`，覆盖 ORM/迁移一致性、完整升降级和已有审计保护。另执行受影响的作战室聚合测试通过；Ruff 和 mypy 的受影响范围检查通过。本切片没有运行与报告无关的完整回归。

## 限制与下一步

- 当前只有 JSON API，工程师还不能在页面查看或下载报告。
- `actor_id` 尚无认证保证，报告哈希也不是外部签名。
- 没有改进项、负责人和截止日期的持久模型。
- 下一步建议在 Incident 作战室为 closed 事故增加报告生成/查看入口，并由前端基于结构化快照渲染可打印内容。

## 面试表达

> 我没有让模型在事故结束后自由写复盘，而是先做确定性的事实快照。只有 closed Incident 能生成，生成事务锁定事故并复用作战室聚合，再冻结完整时间线和 SHA-256。重复请求返回同一记录，读取时重新验结构和哈希，因此报告既可审计又可复现；需要总结润色时，未来也只能把这个快照作为受控输入。
