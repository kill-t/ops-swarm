# 61 - 复盘改进行动项前端闭环

## 目标

在 Incident 作战室的冻结复盘报告下，增加行动项读取、人工创建和受版本保护的完成功能，让第 60 步的后端责任跟踪真正可由值班工程师操作。

## 设计与边界

- 使用独立 Pinia store 管理当前报告的行动项，不扩大 Incident store。
- 以报告 ID 和递增请求代次隔离切换页面后的迟到响应。
- 创建草稿持有稳定幂等键；内容未改变的失败重试不生成新键。
- 完成请求的版本来自当前行动项，组件不能提交任意版本。
- 版本冲突后刷新最新列表但不自动重放完成命令。
- 可变行动项位于不可变报告打印区域之外。
- 本步不修改后端、数据库、认证、通知或外部工单系统。

## 实际改动

- 新增行动项 TypeScript 请求、响应和状态契约。
- API 客户端新增列表、创建和完成调用。
- 新增 `report-action-item` Pinia store，负责排序、响应归属校验、幂等结果合并、冲突刷新和请求代次。
- 新增 `ReportActionItemsPanel`，展示责任、截止时间、逾期提示、创建审计和完成审计。
- Incident 作战室监听冻结报告 ID，自动装载或清理行动项状态。
- 增加响应式表单、行动项卡片和完成状态样式，保持打印报告边界不变。

## 限制与下一步

- 当前没有认证，责任人和操作者仍是本地字符串。
- 没有跨事故行动项总览、逾期筛选和责任人筛选。
- 没有提醒、重开、编辑或外部工单同步。
- 下一步优先建立跨事故的改进行动项治理视图，而不是继续增加 Agent 数量。

## 面试表达

> 我没有把可变行动项塞进不可变报告对象，而是建立独立 Pinia 状态域。创建草稿保存幂等键以覆盖网络不确定性，完成命令从服务端投影取乐观锁版本。冲突时只刷新最新事实，不自动升级版本重试；报告切换则用请求代次防止迟到覆盖。这样前端交互不会削弱后端幂等和审计语义。
