# 恢复演示的远端登记回执时钟诊断

2026-11-14。恢复脚本复测在 CAS 后中断断言失败。为测试加入有限诊断，保留 Worker 是否工作、阶段、尝试与结果码、远端请求方法和准备窗口。输出不包含访问令牌或远端响应正文。

隔离 PostgreSQL 复现时 Worker 已领取，持久任务为 `dispatched`、结果为 `unknown / release_dispatch_invalid`。准备窗口仍有效，远端仅收到登记 `POST` 和对账 `GET`，未收到执行 `PUT`。这将首个失败边界定位到登记回执校验。

随后停止恢复长链，使用隔离容器里的实际登记接口做最小探针。同一份 `201` 回执以其数据库 `checked_at` 作为对照观察值时通过完整结构校验，以 Windows 宿主机当时的 UTC 作为实际客户端观察值时被拒绝，数据库时间领先约 349 毫秒。另一次 20 秒直接采样也确认两个时钟存在偏差。最小探针保存在 `.pytest_cache/probe_dispatch_clock.py`，执行 `python -m pytest -q -s -p tests.conftest .pytest_cache/probe_dispatch_clock.py` 通过，成功标准是重现原时间守卫的拒绝。

上述证据复现同一登记回执失败机制。原长链未采集原始回执时间，因此不追溯断言其精确差值。接下来在 UTC 稳定的独立 Linux 环境对同一构建复验。恢复长链与三条正式发布场景仍待验收。

面试表达：以持久结果码和远端方法区分登记、执行与对账。登记记录已落库，但未来回执触发拒绝，Worker 只查询原操作，没有写出 CAS。
