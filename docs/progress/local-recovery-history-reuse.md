# 恢复采样复用完整执行历史守卫

隔离发布复验中，恢复任务首个尝试过期后重领，最终取得同次尝试的三份 200，但事故收敛已越过原样本有效期。现场记录见[重启复验](local-release-restart-verification.md)。

恢复授权、样本保存和收尾反复读取冻结的完整执行来源。改为复用 PostgreSQL 既有 `assert_release_job_history`，随后继续用原 Pydantic 请求契约和执行视图重建。历史守卫拒绝转换为恢复完整性错误；实际写出仍由发布执行入口校验当前权限。本片遵循原 30 秒租约及 120 秒恢复窗口。

对已阻断和已应用的两个存量案例，对照视图完全一致，来源重建耗时分别从约 5.1 秒降至 3.2 秒、1.8 秒降至 1.2 秒。API 回归增加上游条件审批摘要损坏时的拒绝校验，在领取前验证读取与领取均关闭；后续有效采样使用正常租约。验收辅助脚本依据最终结果的尝试身份筛选三份样本，同时记录先前失败样本。

探针、契约与窗口单测、Ruff 和定向 Mypy 通过。真实 PostgreSQL 正常 CAS 恢复、并发单领、跨租约接管、损坏拒绝、两类来源收尾与事故收敛通过。故障 CAS 变体在进入恢复前的执行夹具中得到 `unknown`，该前置欠项单列。新增攻击初次放在采样租约内时，恢复后的观测已超过十秒，改为领取前验证上游损坏后，定向复验通过。测试期间停止本任务发布栈并保留卷，使用独立临时 PostgreSQL。

定向回归使用恢复 API 的 `single_claim_persisted_samples`、`read_permissions_versions`，以及收尾和收敛 API 的 `two_sources` 正向用例。完整 Compose 正常恢复收敛继续复验。

面试时可说明如何复用已实现的历史完整性校验缩短采样路径，并用稳定任务身份、新尝试身份和有效期约束保证恢复结论可追溯。
