# 恢复采样准入的有界等待

按授权停止 Docker Desktop、重置 WSL 后，原卷恢复和整栈就绪检查通过。发布头仍为 stable、修订 35，原 `source_failed/held_uncertain` 及保留槽位未改变。冷启动时钟探针出现相对校正，就绪后的三十秒探针未复现 UTC 倒退；Windows 同期未见明显跳变，不能据此宣称环境问题永久消除。之后标准案例仍在写出前失效，执行迟滞尚未完全定位。

保留标准启动命令的临时协程栈诊断案例完成唯一回滚至修订 39，随后捕获恢复 Worker 的 `recovery_sample_too_early` 未处理退出。固定睡眠两秒不等于下一次 UTC 准入必然成立。诊断入口已撤回，后续以标准装配验证，事后独立 HTTP 200 不替代原业务样本。

Worker 现在仅对提前准入继续等待并重新核验，保持同一尝试、租约和样本序号。全部采样共用一个单调等待截止，原三十秒 UTC 租约、一百二十秒窗口及最小采样间隔继续生效。失租或等待截止后交回扫描；来源损坏及存储自身超时继续拒绝，不能伪装成恢复或来源失败。规则见[恢复设计](../architecture/128-candidate-recovery-verification.md)。

新增 Worker 单元覆盖等待后成功、失租、共享截止、其他错误传播及探针失败保留；原契约、窗口及 HTTP 探针回归通过。真实 PostgreSQL 的正常 CAS/恢复用例注入一次额外等待，验证仍为一个尝试、三份逐次持久样本和三次业务探针，父事实保持。Ruff、定向 Mypy 通过，数据库迁移及协议未变。测试采用假模型与进程内演练端口，标准 Compose 的完整恢复收敛待部署复验。

面试时可说明固定延迟与业务准入的区别，以及如何在保留原授权、租约和资源上限的前提下处理可等待状态。

诊断时查阅 [py-spy 官方说明](https://github.com/benfred/py-spy#dump)（2026-11-07），仅用于进程外调用栈读取，未读取局部变量或修改业务镜像；该次独立采样未定位执行迟滞，不作为恢复证据。
