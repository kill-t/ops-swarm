# 复用已核验的人工重评准备来源

在仅启动 PostgreSQL 的隔离发布卷上，读取同一个历史执行任务的完整来源。原路径发出 543 条 SQL。准备视图已经核验并重建冻结来源，重评读取随后又重建一遍。现在让准备读取在同一事务内一并返回视图和已核验来源，保留既有准备视图接口。

使用同一镜像、同一历史任务和只读挂载复测，SQL 数量从 543 降到 344，累计 SQL 执行时间从约 1.11 秒降到约 0.72 秒。两次总耗时约 2.18 秒和 2.28 秒，单样本无法证明端到端缩短。探针脚本和输出留在项目忽略目录。

真实 PostgreSQL 的重评精确输入及既有事实保留用例通过，Ruff 与 Git 差异检查通过。

通过标准发布入口复验新事故，实际变更取证、人工续接、候选、审批和同键派发均成功。领取到派发标记耗时约 4.9 秒，写入标记时窗口还剩约 16.6 秒。注册 POST 等待响应超时，只读 GET 返回 404，控制面保存 `unknown` 和 `release_dispatch_timeout`。隔离数据库未找到该操作的远端登记和 CAS 记录，订单版本维持回滚前的修订，业务探针仍为 HTTP 500。事后从同一执行容器访问健康和演练状态接口均返回 200。这些读取没有定位注册超时发生在连接、服务处理还是数据库锁等待。下一步仅对新操作测量注册路径和数据库等待，再复验正常恢复。

面试时可区分单次核验结果的事务内复用与跨事务复用。前者消除同一次调用的重复遍历，后续派发与执行前依然独立核验当前状态。
