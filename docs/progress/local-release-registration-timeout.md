# 远端注册等待与固定窗口复验

在隔离发布网络从执行容器发起独立的新注册探针。一次自然等待中，客户端已开始接收响应头但在 3 秒后超时。PostgreSQL 同期采到事务锁等待，随后 GET 读到已注册的操作。无锁对照返回 201，耗时约 0.2 至 0.5 秒。原发布事故的注册超时没有独立锁样本，探针证明该现象可由发布头行锁等待产生。

用独立事务暂持发布头行锁 4 秒。3 秒等待产生读超时，6 秒等待在约 4.3 秒收到 201。每个探针随后只读对账并取消登记，没有执行 PUT，版本和修订一致。基于此结果，隔离发布执行 Worker 使用 6 秒 HTTP 等待，现有 30 秒派发窗口及数据库截止检查继续适用。

合并基础与发布 Compose 配置后，`docker compose config --quiet` 通过。用常驻发布 Worker 与脚本模型复验新事故，从人工准备和重评推进到可信审批及派发。同键重放复用派发任务，回滚结果为 `applied_current`，订单版本由 `rc1` 切为 `stable`，修订号只从 14 增至 15。

正式恢复采样在首个请求记录 `probe_timeout`，恢复结果为 `source_failed`。持久收敛结果为 `held_uncertain`，事故维持 `mitigating`，保留活动槽位。此次验收覆盖派发与回滚，完整恢复仍待验证。下一步从恢复 Worker 定向测量固定订单 GET，区分服务响应和容器调度耗时，再按证据复验。

面试可用这组对照解释为什么传输超时后只能查询原操作，以及为什么传输等待与业务授权截止需要分别验证。
