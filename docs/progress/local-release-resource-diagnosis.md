# 隔离发布执行耗时与资源诊断

六秒传输等待后的标准发布案例仍未通过完整恢复验收。运行 `d8614519-4834-4ae8-9338-a2293135c0b0` 在派发前因来源时效停止；随后用新运行 `35df2820-48b7-4606-9387-cfcb798af319` 对既有执行入口增加临时分阶段计时，未替换返回值、守卫或业务期限，模型仍为隔离脚本模型。

新案例领取约五秒，派发前完整来源读取约五秒，涉及三百余条查询；事务提交不足一秒。远端注册调用随后约十秒超时，只读对账返回操作不存在，任务持久化为 `unknown/release_dispatch_timeout`。数据库日志进一步记录该注册 INSERT 在固定窗口结束后被原生守卫拒绝。对应操作 `5a0a2f5c-103d-54bf-99ed-b2664c223144` 无持久派发记录，发布头保持 `2026.01.01-rc1`、修订 28，不能表述为已回滚或已恢复。

独立只读 HTTP 探针中，TLS 上下文初始化为毫秒级，未复现这段延迟；不能据此修改 TLS 校验。原生执行历史守卫的独立只读探针约两秒，不能归因于某条持续阻塞的 SQL。执行阶段仍有重复重建开销，但当前证据不足以认定它是全部超时的唯一原因。

同时采集的 Docker 虚拟机约 3.77 GiB 内存、1 GiB 交换空间已用满。内存压力 full 的十秒均值约 52%，I/O 压力 full 约 77%；Windows 当时可用物理内存约 570 MiB。这是实际资源压力证据，不能直接证明所有历史失败均由内存导致。暂不继续完整长链或放宽三十秒派发、六十秒执行租约等业务限制。

临时停止本次正常场景不使用的六个回流 Worker 及经验 Worker 后，虚拟机可用内存从约 0.5 GiB 升至约 1.3 GiB，内存与 I/O 压力 full 的十秒均值分别降至约 2%。该对照支持先处理整栈资源压力；并非完整发布验收，不能以少启动组件替代标准装配。对照后恢复原服务，数据卷保留。

分阶段诊断入口仅以忽略缓存中的 Compose 覆盖文件挂载；执行 Worker 已恢复正式模块命令。详细阶段、数据库、订单服务与资源报告保存在 `.pytest_cache/compose-local-smoke/`，不提交日志、凭据或缓存。后续先消除选定验收环境的资源压力，再复验正常恢复、事故收敛及槽位释放；完整行为仍未验收。

面试时可说明：HTTP 超时不等于操作未发生，应结合原操作查询、数据库守卫与发布头核对副作用；应用阶段计时和系统压力证据分开记录，避免通过延长授权窗口掩盖环境问题。
