# 重启后的发布复验

经用户授权重启 Docker Desktop，使用原命名卷恢复隔离发布栈。测试身份续期四小时后重新装载，迁移与发布预检成功，原事故仍为 `mitigating`，收敛记录为 `held_uncertain` 且保留槽位。数据库与本机 UTC 接近。模型由隔离网络内的脚本端点提供。

恢复 Worker 的三次原始探针和三次带计时探针均返回 200。随后首个新事故通过调查、人工续接、候选评估和可信审批，但任务从创建到首次领取约经过 36 秒，已越过原派发截止，结果为 `release_execution_source_stale`，远端登记数为零。事后重建历史和来源均可在较短时间完成，终态同键重放保留原任务及原结果。十秒时钟对照未复现明显跳变，先前延迟的具体原因仍待定位。

为区分排队与复核耗时，第二个独立事故使用临时阶段计时包装，沿原 Worker 主入口、HTTP 客户端与业务检查推进。计时材料保存在忽略的缓存目录，验证结束恢复标准 Compose 命令。

该事故在创建发布准备请求时返回 `candidate_release_observation_timeout`，尚未创建准备请求和执行任务，订单保持故障版本及修订 18。同期有限数据库采样未捕获锁阻塞。阶段计时包装已撤销，执行 Worker 恢复 `python -m opsswarm.execution.release_jobs.main`。

控制 API 容器内直接调用发布头观测器，三次读取均成功，首次约 2.7 秒，接近默认 3 秒传输上限。进一步分段探针在 70 秒内未取得容器输出。现有结果尚不能将超时归因于客户端初始化、网络、服务端或锁等待。诊断结束时执行 Worker 的容器命令已核对为标准入口。

继续复验时，新事故在相同观测边界被拒绝。为定位实际请求，在控制 API 临时增加计时，沿用仍有效的审批，以新幂等键重试发布准备，保留原失败命令审计。观测约 0.2 秒完成，派发及同键重放通过，回滚将修订 20 切至 21、版本变为 `stable`。API 的标准启动命令随后恢复。

正式恢复的首个尝试租约过期，第二次尝试完成同次三份 200，恢复结果为 `recovered`。事故收敛发生在原 120 秒采样窗口结束后，结果为 `held_stale`，槽位保留。验收辅助脚本已按最终结果的尝试身份筛选样本，保留先前失败样本。持续时钟采样还捕获了 UTC 相对单调计时的正、负调整，环境时间问题继续单列。下一步缩短恢复与收敛路径的重复历史重建，完整正常恢复收敛仍待验收。

验证采用 `docker desktop restart --detach`、合并 Compose 的 `up --no-build --wait`、同源 API 和只读 PostgreSQL 查询。记录本次已完成的环境恢复与实际失败边界，完整发布继续开发。文档链接与 Git 差异检查通过。

面试时可说明如何用持久记录、只读探针和阶段计时定位端到端问题，并以正式业务样本作为恢复依据。
