# 发布审批来源的单次遍历复用

标准栈部署采样等待修复后，新案例的首次发布准备观测超时；在原授权和预算内重试新命令后创建执行任务，但写出前仍已过期，修订 40 未回滚。旧运行的预算随后到期，不继续沿用。完整正常收敛尚未验收。

同一历史请求的只读对照发现，审批来源的顺序读取分别重建四类共同祖先。扩展已有的[有界来源核验作用域](../architecture/110-bounded-source-validation.md)，让发布请求的完整只读重建共享一次遍历。作用域仍绑定运行、会话、事务和协程，退出时再次检查依赖并清空；不跨业务写入、网络请求或事务复用，不缓存当前身份、预算及窗口资格。未新增缓存平台或迁移。

对同一完整来源按正反顺序对照，SQL 均由 344 条降为 168 条，返回对象完全相同。该结果只证明重复读取减少，不代表整栈期限问题已经解决。

真实 PostgreSQL 的作用域边界、三轮检查点恢复及写前身份撤销、预算和版本变更用例共 28 项通过；发布请求单元测试 84 项通过，Ruff 与定向 Mypy 通过。原正常 CAS/恢复用例两次停在前置登记，未发送执行请求；最小探针表明派发材料的数据库时间早于由 Windows 时钟写入的发布状态时间，严格校验正确拒绝。随后在临时 Linux 测试容器内，使用当前源码、锁定测试依赖及隔离 PostgreSQL，同一正常 CAS/恢复用例通过：实际回滚后一个尝试保存三次业务采样，并处理一次提前准入。未改变时间守卫或测试行为，跨时钟夹具问题不写成已修复。

可复现验证入口为 `tests/integration/test_source_validation_scope.py`、三轮来源用例的 `[True]` 变体、`test_release_execution_jobs_api.py` 的写前变更用例及 `test_candidate_recovery_api.py` 的正常实际 CAS 用例，数据库使用 PostgreSQL 17.6、`PGOPTIONS=-c jit=off`。最后一项使用同钟 Linux 环境；临时容器和数据库均已自动清理。详细命令、对照脚本和日志留在忽略缓存。

下一步部署标准镜像，以新案例核对唯一回滚、逐次恢复样本、事故收敛及槽位释放。面试时可说明一次来源遍历与跨操作缓存的区别，以及如何用查询计数、结果等价和并发变更拒绝共同验证优化。
