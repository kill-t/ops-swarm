# 发布执行事务与恢复超时诊断

包入口整理后的标准案例 `9647390a-896b-457d-b82b-f4a5264435a5` 仍在写出前失效，发布头保持故障版本、修订 32。同期内存和 I/O 压力已明显低于前一案例，不能将全部失败归于资源压力。同一来源的独立只读探针首次重建约两秒、复读约一秒，无法单独解释实际尝试的四十余秒耗时。

新案例 `2fe01cc9-e2d8-48ad-8222-580975a218c6` 仅对既有执行方法增加计时，同时只读采集数据库活动及阻塞关系；未使用自动执行计划分析、替换业务返回值或改变期限。首次领取约两秒，派发前来源读取约七秒，锁获取、写入和提交均未出现长等待。本次未复现四十余秒延迟，不能宣称其根因已定位。

同键重放复用原任务，原三十秒窗口内完成唯一回滚，发布头从修订 34 推进为 stable、修订 35。随后正式恢复首次探针超时，结果为 `source_failed`，事故收敛为 `held_uncertain`；Incident 保持 `mitigating`，运行已收尾但活动槽位保留。后续独立只读 HTTP 探针取得 200，仅是诊断，不替代或改写原恢复结果。采样期间未捕获发布头锁等待；根事务提交曾阻塞其他父工作项查询数秒，尚不能将它认定为 HTTP 超时原因。

执行计时还出现 UTC 增量小于单调时钟增量的情况。独立三十秒探针进一步捕获两次 UTC 倒退，单步约 0.15 和 0.29 秒，单调时钟同期持续前进。此异常直接关系到租约、未来时间及观测时效校验，须按[交付设计第七节](../architecture/local-multi-agent-release-scope.md#7-141与时钟问题独立处理)先处理选定环境，不能放宽守卫。当前 WSL 同时运行 Ubuntu 22.04 和 Docker 后端，重置 WSL 会中断两者，必须另获明确授权。

临时执行入口已撤回并确认标准模块命令，数据卷及全部诊断事实保留。完整正常恢复收敛仍未验收。详细阶段、锁等待、HTTP 和时钟报告留在忽略缓存；本次文档只检查事实、链接和差异，不重复已通过的业务测试。

面试时可说明如何用持久副作用、事务阶段、数据库等待和独立时钟探针逐步缩小范围，并明确区分实际恢复样本与事后诊断。
