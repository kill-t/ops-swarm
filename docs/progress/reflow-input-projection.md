# 现场失败回流输入投影

新建现场 graph-v16 调查运行固定 `reflow-projection-v1`。数据库约束将策略限定在现场图版本，并拒绝修改已创建运行的策略。迁移前的运行继续按原策略重建。完整冻结材料及哈希用于审计，模型请求仅携带各阶段需要的业务字段。实现规则见[现场回流设计](../architecture/live-reinvestigation-handoff.md)。

同一冻结案例使用原 48,000 单次输入上限离线回放，四阶段估算由 52,373、53,974、64,676、67,862 降到 25,555、26,191、26,466、29,304。后三阶段仍使用离线占位证据和结果。构造仅在内存给历史样本补入新策略标记，无数据库写入或模型调用。隔离演练库从 `0099_live_reflow_handoff` 升到 `0100_reflow_input_projection`，元数据检查通过，原阻断作业仍能重建同一来源哈希与预算阻断。

隔离 Compose 使用原 48,000 单次上限、500,000 累计输入上限和 1,800 秒期限，用脚本模型复演同一故障。回滚中断后只读对账一次，版本修订号由 18 增至 19，随后连续三个探针返回 HTTP 500。一次准入成功，同键重放返回原记录，第二个键收到 409。新窗口实际读取到连接池变更，经过综合和独立复查后持久记录 `await_human` 和 `live_reflow_manual_takeover`。四阶段持久估算为 23,009、24,194、24,493、27,412。原账本 9 条调用记录完整保留，总记录增至 14 条，无未结预留，截止时间相同。事故继续调查，唯一活动槽位归原运行，原处置操作仍为一条。

定向单元测试、真实 PostgreSQL 空库迁移往返、元数据及 Ruff 检查通过。用冻结案例对比协调、综合及独立复查的 Python 和 SQL 输入包，三者完全一致，专业输入通过 Compose 中的原生写入守卫。宿主机运行的进程内 API 长链两次在原回滚阶段触发 `release_dispatch_invalid`，未进入本次新增断言，已停止整链复跑。Compose 的独立验证完成了现场失败回流。复现使用[既有 Compose 演练](local-compose-continuation.md)的脚本和隔离项目，切换到含本迁移的运行镜像，详细日志留在项目缓存目录。

面试可以沿一次调用展示完整来源的哈希、投影后输入的哈希和预算预留。两个哈希分别验证审计来源及实际模型请求，运行固定策略使旧包可按原规则重建。
