## 小证据集的按需取证增加整次调查开销

2026-11-05。使用 DeepSeek Flash 对 5 个 RCAEval RE2 故障注入案例做配对评测。输入为日志和指标生成的小体积摘要，每个案例每种策略运行一次。

| 指标 | 直接提供全量摘要 | 目录与按需读取 |
| --- | ---: | ---: |
| 故障服务定位正确 | 4/5 | 4/5 |
| 总 Token | 9,463 | 11,172（+18.1%） |
| 耗时中位数 | 1.24 秒 | 2.55 秒 |

**工程判断。** 这个场景里，额外模型调用和重复提交上下文的开销超过了少读证据的收益。下一步在未参与调试的案例上按证据体积分层，验证小证据直接注入、长证据按需读取的分流策略。分流阈值和收益仍待实测。

**简历表述。** 基于 RCAEval RE2 和 DeepSeek Flash 搭建 5 个案例的配对评测，测量整次调查的准确率、Token 和时延。发现小证据场景下，按需读取在定位结果同为 4/5 时增加 18.1% Token，据此提出按证据体积分流的验证方案。

**面试追问。** Token 采用供应商报告的整次调查用量，计入工具前后所有模型请求。五个案例参与了试点调试，结论限于该批日志和指标摘要。实验在独立回放入口运行，业务 Worker 和动态多 Agent 另行评测。

## 证据分流降低用量，仍有诊断质量代价

2026-11-05。在同一系统的 6 个新案例上，用 DeepSeek Flash 做 24 次配对调查。约 4 KB 摘要按需读取多用 15.1% Token；约 20 KB 扩展证据按需读取少用 44.2% Token。扩展组的故障服务定位从 6/6 降到 5/6，耗时中位数从 1.75 秒升到 3.08 秒。

**工程判断。** 按预先设定的字节阈值做离线分流，整批用量从 89,001 降到 54,766 Token（−38.5%），定位从 12/12 降到 11/12。先复盘按需组的网络延迟误判，再验证追加取证能否改善诊断质量。当前结果可用于选择后续实验，尚未接入业务调查。

**简历表述。** 用 DeepSeek Flash 在 6 个公开故障案例上完成 24 次配对调查，验证按需取证的成本随证据体积变化。离线回放中，按体积分流较始终全量少用 38.5% Token，定位为 11/12，识别出一项需补证的网络延迟误判。

## 十五例留出验证达到取证优化停止线

2026-11-05。用 DeepSeek Flash 对 15 个未参与前两批的公开故障案例做 30 次配对调查。在约 20 KB 扩展证据上，按需取证把总 Token 从 192,836 降到 104,831（−45.6%），定位由 15/15 降到 14/15，耗时中位数增加 1.082 秒。完成率、定位、用量和耗时均满足预设门槛。

**简历表述。** 在 15 个公开故障案例上完成真实模型配对评测。约 20 KB 证据场景下，按需取证较全量摘要减少 45.6% 总 Token，定位正确 14/15，并明确了额外请求带来的时延及误判代价。

**工程决定。** 本轮按预设门槛收口。唯一误判已读取正确服务，追加读取上限缺乏直接依据。当前数据来自同一微服务系统，适用范围为离线调查试验。下一项用同一模型、证据和预算比较单 Agent 与动态多 Agent 在简单题和需补查任务上的质量、时延及 Token。

## 专业协作在网络故障组提高定位准确率

2026-11-05。用 DeepSeek Flash 在 15 个新案例上做离线配对回放。日志与指标专业分工加汇总，使网络故障组定位从 8/10 提升到 10/10，资源故障组维持 5/5。总 Token 从 30,155 增至 49,784，耗时中位数增加 2.604 秒，均在预设门槛内。

**简历表述。** 设计并执行 15 例公开故障的真实模型配对实验，量化日志和指标协作在网络故障中的收益（8/10 → 10/10）及代价（总 Token 约 1.65 倍、中位时延增加 2.60 秒）。

**范围。** 协作组始终选择两个角色，未触发补查。数据支持本批的专业分工和汇总组合，不能据此量化动态补查收益。下一步转向实际产品 Harness 的中断恢复。

## 成功调用已落库时，恢复可避免重复请求

2026-11-06。在真实 PostgreSQL 和 checkpoint 的产品 graph-v16 测试中，于第二轮审查的模型成功记录落库后、业务事实提交前中断。新 Worker 使用原调查恢复，额外 SDK 请求和重复取证均为 0，预算快照保持一致，最终只保存一条终端交接事件。

**简历表述。** 在实际产品 Worker 与 PostgreSQL checkpoint 的两轮调查中注入提交前故障，验证恢复复用已成功模型调用，额外请求与取证均为 0，预算账本保持一致，并完成唯一的终端交接。

**范围。** 模型及 MCP 客户端使用脚本响应；结论适用于成功调用已落库的指定窗口。时序对照为本地单次测量。

## 回滚生效后中断，接手 Worker 可只读对账

2026-11-06，在隔离 Docker Compose 演练中，订单服务回滚成功后、控制面结果写入前退出执行进程。首个租约到期后，新进程发出 1 次 GET、0 次写请求，保存同一操作的结果，版本修订号保持在 17。另一场景验证了三次新鲜 HTTP 200 后关闭事故，样本超时的对照运行则保持在缓解中。

**简历表述。** 设计并实测高风险处置的幂等派发、租约接手与只读对账，在回滚生效后注入进程中断，验证恢复过程零重复写入。使用连续业务探针独立验证事故恢复。

**范围。** 真实 PostgreSQL、独立执行进程与本地故障演练服务。模型为脚本响应。

## 再调查输入触发预算护栏

2026-11-06，演练回滚完成后，独立连接池故障使三次业务探针仍为 HTTP 500。系统接受一次再调查请求，但协调输入在调用模型前超过预算。只读重建输入得到 52,117 字节，约 28.7 KB 来自原调查材料。项目估算器给出 52,373 个输入 Token，高于 48,000 的单次上限。

**工程决定。** 先检查历史输入中的重复材料和各字段的实际消费方，再用相同预算做配对验证。保留原证据出处、反证、人工约束和共享账本。优化收益与后续接管仍待实测。
