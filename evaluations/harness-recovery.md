# 产品 Harness 中断恢复验收

2026-11-06。范围是现场 v3 graph-v16 的第二轮审查。使用产品 Worker、业务 PostgreSQL 和 PostgreSQL checkpoint。模型 SDK 与 MCP 客户端端口返回脚本化数据，固定两个调查轮次。正常组和中断组采用同一经验配置、证据和预算。

在第二轮审查的模型成功记录落库后、审查事实保存前注入异常。随后关闭原 checkpoint 连接，构建新 Worker 与连接，在同一调查运行上重领并恢复。

| 验收项 | 通过条件 |
| --- | --- |
| 中断边界 | 运行可重新领取，保留成功调用；第二轮审查和终端交接尚未提交 |
| 恢复后的调用和取证 | 额外 SDK 请求为 0，已提交证据无需重新读取 |
| 预算 | 恢复前后账本完整相等，包含调用身份、用量和原截止 |
| 业务事实 | 两轮任务保持原身份，最终恰好两条审查与一条交接事件，释放租约 |
| 性能观察 | 记录 Worker、分派、调查、综合、审查及代表性持久化方法的墙钟耗时。阶段可能嵌套，不能相加推导总耗时 |

复现命令使用项目已有的临时 PostgreSQL 测试容器。数据库会话应使用 UTC。

```powershell
.venv/Scripts/python.exe -m pytest -o junit_family=xunit1 tests/integration/test_live_dynamic_workflow.py --junitxml=.pytest_cache/harness-recovery.xml -q
```

用例 XML 的 `harness_recovery_measurements` 属性保存每次的阶段耗时和计数。恢复正确性通过后先收口。脚本模型的单轮耗时用于定位下一项采样对象，真实服务延迟需要另行采样后才能评估优化。

## 实测结果

三个集成用例通过。下表比较经验配置相同的两次，另一次关闭经验的基线也通过。Docker 引擎停用期间，使用 [Windows PostgreSQL 17.11 发行包](https://www.npmjs.com/package/@embedded-postgres/windows-x64/v/17.11.0-beta.19)在仓库缓存内启动隔离实例，业务与 checkpoint 使用独立数据库，正常结束后关闭实例。

| 观察量 | 正常基线 | 注入中断并恢复 |
| --- | ---: | ---: |
| Worker 尝试 | 1 | 2 |
| 已发送模型请求 | 9 | 9（恢复阶段 0） |
| 遥测读取 | 2 | 2（恢复阶段 0） |
| 账本预留 | 9 次模型、4 次工具 | 相同，恢复前后快照一致 |
| 审查事实与终端交接事件 | 2 条审查、1 条交接 | 2 条审查、1 条交接 |
| 首次 Worker 处理 | 15.279 秒 | 10.486 秒 |
| 第二次 Worker 恢复处理 | — | 6.093 秒 |

正常基线的分派为 0.321 秒，两次专业调查分别为 0.401、0.878 秒，两轮综合为 0.645、2.221 秒，两轮审查为 1.895、3.404 秒。第二轮审查内的事实保存为 0.780 秒，最终交接保存为 0.360 秒。详见[逐阶段 JSON](harness-recovery-measurements.json)。当前只有单次对照，且模型和遥测固定响应，阶段数据仅作为后续采样线索。可优先细分第二轮审查中的来源复核与数据库读写，再决定是否调整链路。

原生 PostgreSQL 默认会话时区为 `Asia/Shanghai` 时，首轮在协调计划来源核验处失败。最小探针显示，同一时刻的 UTC 与 `+08:00` Python 值相等，但当前来源比较序列化后不同。改用 `PGTZ=UTC` 建立新的隔离数据库后通过。该差异是本轮验证发现的环境前置条件，产品的来源比较逻辑尚未调整。

结论限于成功调用已落库后的指定中断窗口。本用例重建 Worker 对象和 checkpoint 连接，进程级退出及 Compose 重启仍属于独立发布验收。
