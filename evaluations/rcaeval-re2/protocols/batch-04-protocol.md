# 第四批单体与动态协作回放

2026-11-05。固定 15 个未出现在前三批的 RCAEval RE2 案例。按注入类型分为资源故障 5 例（CPU、内存、磁盘）和网络故障 10 例（延迟、丢包、套接字）。这是预设分组，网络组作为较易出现跨服务症状的代理，实际是否补查由模型决定。使用原有版本的紧凑和扩展日志、指标。模型不接收分组、原文件名、故障标签或注入时间。见[清单](../cases/batch-04.json)。

现有产品冻结 Worker 的数据入口固定在本地订单演练，单 Agent 结论也使用 MVP 根因枚举。此处在独立离线入口比较组织方式，评分采用 RCAEval 的故障服务标签。结果适用于本协议的调查策略。产品 v3 的 Worker、账本、checkpoint 和审批链有各自的验收。

| 模式 | 首轮 | 可选补查 |
| --- | --- | --- |
| 单 Agent | 同一个调查者查看紧凑日志和指标，提出诊断 | 可请求至多 3 个服务的扩展证据，再给结论 |
| 动态协作 | 协调器根据数据目录选择日志、指标之一或两者。专业角色各看自己的数据，两角色可并行，汇总者结合报告作诊断 | 同样可请求至多 3 个服务的扩展证据，再给结论 |

真实 `deepseek-flash`，温度 0，关闭思考。每例每组一次，按案例交替顺序，共 30 次调查。每次共享上限为 5 次请求、48,000 输入文本字节，每请求最多 384 输出 Token。按请求累加供应商用量；有缺失则整次用量标为未知。评分以单一服务 Top-1 为准，同时报告角色分派、补查触发及改判、完成率、总 Token 和墙钟中位数。

## 停止线

开始运行前固定下列门槛。两组均完成 15/15 且用量完整。动态协作在网络组至少多正确 2 例，资源组至少与单 Agent 正确数相同。整批动态协作总 Token 至多为单 Agent 的 2 倍，耗时中位数最多增加 3 秒。

全部达标即收口。未达标时，只有记录能指出具体、可复现、可用一次变更修正的问题，才另用 15 个新案例复验一次。两批为上限，之后保存收益与代价，转向独立审查或中断恢复。凭据、模型访问或网络中断单列，不参与策略门槛判定。
